# 存量指标口径发现方案（Metric Caliber Discovery）

> 2026-08-30 | 飞熊 × dev
> 背景：DataWorks 原生只有"正向登记"指标口径（智能建模→数据指标，页面手工建或 Excel 批量导入），逆向建模只能反向表结构、反不了口径。存量数仓跑了两年的指标，口径散落在 ETL SQL、字段命名、报表计算字段里，需要一条逆向发现流水线。

## 0. 结论先行

- **没有现成的"口径自动发现"开源产品**，能直接用的只有零件：sqlglot（解析引擎）+ 血缘 + LLM 起草，组装活要自己干
- **实测结论**：sqlglot 30.17.0 无 odps 方言，但 `read='hive'` 可完整解析 MaxCompute ODPS SQL（INSERT OVERWRITE + PARTITION + SUM / COUNT DISTINCT 聚合全部提取成功）
- 核心自研量约 200 行：ODPS 语法边缘 case + 口径归一化规则，其余全是组装
- 产出对齐 DataWorks 数据指标模型（原子指标 + 修饰词 + 时间周期），可直接 Excel 批量导入回 DataWorks，或落 cubepy measure

## 1. 总体流水线

```
P0 采集 → P1 解析提取 → P2 命名拆解 → P3 指纹聚类 → P4 LLM起草 → P5 人审入库
SQL语料库   候选口径对象   原子/修饰/周期  冲突检测     口径描述     防漂移
```

## 2. P0 数据采集（喂料）

| 源 | 拿法 | 内容 |
|---|---|---|
| DataStudio 节点 | OpenAPI `ListFiles` + `GetFile`，或导出工作流 zip | 全部 ETL SQL（口径主来源） |
| MaxCompute 元库 | `INFORMATION_SCHEMA`（TABLES / COLUMNS / TASKS_HISTORY） | 表/列注释、真实跑过的 SQL 历史 |
| BI 层 | QuickBI 数据集 API | 计算字段 SQL（口径暗藏重灾区） |

产出：SQL 语料库 + 表/列注释字典。

## 3. P1 SQL 解析 → 候选口径对象

sqlglot(`read='hive'`) 逐节点解析，每个聚合投影列生成候选口径：

```python
@dataclass
class CaliberCandidate:
    sink: str            # INSERT 目标表.字段，如 dws_trade_pay_1d.pay_amt_1d
    agg: str             # 聚合表达式，如 SUM(pay_amount)
    dims: list[str]      # GROUP BY 维度
    filters: list[str]   # WHERE 业务限定（排除 ds='${bizdate}' 分区条件）
    source_cols: list[str]  # 源表.源列
    confidence: float    # P2 命名印证后的置信度
```

已验证的提取代码：

```python
import sqlglot, sqlglot.expressions as exp
sql = """
INSERT OVERWRITE TABLE dws_trade_pay_1d PARTITION (ds='${bizdate}')
SELECT buyer_id,
       SUM(pay_amount) AS pay_amt_1d,
       COUNT(DISTINCT order_id) AS order_cnt_1d,
       CAST(SUM(pay_amount)/COUNT(DISTINCT buyer_id) AS DECIMAL(20,4)) AS arpu_1d
FROM ods_trade_pay_info
WHERE ds='${bizdate}' AND pay_status=4
GROUP BY buyer_id
"""
t = sqlglot.parse_one(sql, read='hive')
for sel in t.find_all(exp.Select):
    for p in sel.selects:
        aggs = [a.sql() for a in p.find_all(exp.AggFunc)]  # 每列的聚合链
```

ODPS 特有坑：
1. `${bizdate}` 等调度参数先做占位替换再解析
2. LATERAL VIEW / UDTF 单独处理
3. 动态分区 INSERT 的 sink 提取
4. 多层 INSERT FROM SELECT 逐层穿透

## 4. P2 命名拆解（OneData 词根法，与 P1 互相印证）

`pay_amt_1d_pty_pc` → 原子=`支付金额` + 周期=`1d` + 修饰=`PC端`。

依赖三张词典：
- **原子词根表**：amt/cnt/rate/price/gmv/uv/pv…
- **修饰词表**：pty(终端)/chn(渠道)/cat(品类)/new(新客)…
- **周期后缀表**：1d/7d/30d/nd/wtd/mtd…

印证规则：命名说的和 SQL 说的对得上（词根 amt ↔ SQL SUM，词根 cnt ↔ COUNT）→ 高置信；对不上 → 降级人工。命名规范没执行到位的仓库跳过此步，全靠 P3 聚类。

## 5. P3 指纹聚类 + 冲突检测（价值最高环节）

口径指纹 = `hash(归一化 agg + 维度集 + 过滤集)`，归一化规则：列名小写去引号、常量归一、表达式排序。

三类发现：
| 类型 | 特征 | 产出 |
|---|---|---|
| 口径冲突 | 同名不同指纹 | 冲突清单（`order_cnt` 一处 COUNT、一处 COUNT DISTINCT） |
| 重复建设 | 同指纹不同名 | 归并建议 |
| 孤儿口径 | 只有代码定义、无登记 | 待登记清单 |

跨层传播：用 sqlglot 内置 `sqlglot.lineage` 列级血缘，把 dwd 中间计算传播到 dws/ads 终点指标，一个指标多跳口径串联成完整链路。

## 6. P4 LLM 起草口径

上下文 = 字段注释 + 表注释 + agg SQL + 维度 + 过滤条件 + 上下游血缘 → 批量生成：

```json
{
  "sink": "dws_trade_pay_1d.pay_amt_1d",
  "atomic_metric": "支付金额",
  "modifier": ["PC端"],
  "time_period": "1d",
  "caliber_text": "统计自然日内PC端支付成功的订单金额总和，口径：SUM(pay_amount)，过滤 pay_status=4（已支付）",
  "confidence": 0.9
}
```

输出直接对齐 DataWorks 数据指标模型。

## 7. P5 人审入库 + 持续防漂移

- 审核后导出 **DataWorks 批量导入 Excel 模板**（数据指标模块），或直接生成 cubepy measure YAML
- 持续机制：每周增量解析新任务 SQL → diff 已登记口径指纹 → 口径变更/漂移告警（复用 cubepy-diff 思路）
- 度量指标：候选口径总数 / 冲突数 / 归并数 / 登记率 / 漂移次数

## 8. 开源工具清单

| 工具 | 用途 | 备注 |
|---|---|---|
| **sqlglot** | 解析 / AST / 聚合提取 / 列级血缘 / 转译 | 核心引擎，MIT，零依赖；ODPS 用 hive 方言 |
| **sqllineage** | 表级/列级血缘快速兜底 | 底层也是 sqlglot，交叉验证用 |
| **sql-glider** | CLI 血缘（正向溯源/反向影响分析） | 影响分析不用自己写 |
| **MetricFlow (dbt)** | 指标定义 schema 参考 | 不是发现工具；目标格式对齐它没坏处 |
| **sidemantic** | Cube/MetricFlow/LookML 格式互转 | 与 cubepy 打通可选；**AGPL，只借鉴别抄** |
| **DataHub / OpenMetadata** | 元数据 + 血缘存储展示 | pyom 已对齐 OM，结果存 om_store 即可 |
| OpenLineage | 运行时血缘补充 | 调度侧有埋点才用得上，优先级低 |

## 9. 最小闭环 POC（~200 行，一晚）

1. 拉 10 个核心 dws 任务 SQL → sqlglot 解析 → 候选口径表（sqlglot 包办 80%）
2. 指纹聚类跑全量 → 输出冲突/归并清单（纯 pandas）
3. 候选口径 + 注释喂 LLM → 口径草稿 Excel

## 10. 与 cubepy 的衔接

方案可直接落成 `cubepy/discover.py`，与现有模块同构：

```
autodml reflect ─┐
                 ├→ discover.py（口径发现）→ catalog.py（目录/血缘）→ diff.py（防漂移）
ETL SQL 语料库 ──┘                                          ↓
                                              ai.py（LLM 起草/校验）→ measure YAML
```

机器自动发现候选口径 + 人审确认 20%，与 autodml×cubepy 既定工作流（机器生成 + 人补关键 20%）一脉相承。
