# 指标口径体系构建方案：指标字典 × DataWorks 双源对齐

> 2026-10-24 | 飞熊 × dev
> 背景：公司指标口径管理混乱。现有资产两件——一个指标字典（人工维护，质量参差）、DataWorks 里一堆 DDL + ETL 脚本（口径的事实实现）。目标：用这两者最大程度**精确**构建指标口径体系。
> 前置验证：cubepy `poc_caliber_discovery.py`（58d6fdb / 2550633）已实测 sqlglot hive 方言完整解析 ODPS SQL、目录模式零权限跑通、三类发现（冲突/原子同源/孤儿）全部命中。

## 0. 核心方法论：三方对齐

```
指标字典  =  意图（业务想统计什么，人给的语义）
ETL 脚本  =  事实（实际怎么算的，code is truth）
DDL 注释  =  语境（表/字段是什么，口径线索的中间桥梁）
```

**口径体系的每个条目 = 意图 ↔ 事实 ↔ 语境 三方对齐后的产物。**
只有字典没有代码 → 口径是"宣称的"；只有代码没有字典 → 口径是"无主的"；对齐之后才叫"体系"。

精确度策略：**机器做确定性提取（100% 可证），LLM 做语义匹配（打分），人只审低置信与冲突项。**

## 1. 五阶段流水线

```
S0 资产标准化 → S1 口径发现 → S2 双向对齐 → S3 LLM 富化 → S4 人审回填
 字典/DDL/SQL     候选口径      冲突/漂移      口径卡片      体系落库
     结构化        +血缘链        +孤儿                      +防漂移
```

### S0 资产标准化（把两个输入变成标准件）

**S0.1 指标字典结构化**
- Excel/Wiki → 标准表（CSV/JSON），字段对齐：
  `metric_id | 名称 | 别名列表 | 业务描述 | 公式文本 | 所属域 | 负责人 | 更新时间`
- 清洗：去重、别名拆分（"GMV/总支付金额"→两个别名）、公式文本规范化（全角转半角、去空格）

**S0.2 DDL 解析（sqlglot，确定性）**
- 解析每张 CREATE TABLE → 元数据库：
  `表名 | 分层推断(dwd/dws/ads) | 字段名 | 字段注释 | 分区键 | 命名词根拆解`
- 注释是重要口径线索：`COMMENT '自然日内已支付订单金额'` 直接进语境池

**S0.3 ETL 语料整理**
- 零权限路径（已验证）：DataStudio 导出节点/工作流 → .sql 目录
- OpenAPI 路径（可选，需要定时自动化时再开）：ListFiles/GetFile 全量拉取

### S1 口径发现（POC 已验证，两处扩展）

- **S1.1 聚合提取**（已有）：每脚本 → CaliberCandidate{sink, agg链, dims, filters, source_cols}
- **S1.2 扩展一：DDL 注释增强**：候选口径的源列/汇列反查 DDL 元数据，把字段注释、表用途并入候选语境
- **S1.3 扩展二：血缘多跳串联**：sqlglot lineage 把 ods→dwd→dws→ads 串成完整口径链——ads 终点指标的口径 = 全链聚合（每跳的过滤/清洗规则都算口径的一部分）。这是"精确"的关键：只看一层 SQL 的口径是不完整的
- **S1.4 命名拆解**：公司词根表从两处学习——字典名称 + 数仓字段命名统计（高频 token 人工确认一次），不用通用词根表硬套

### S2 字典 × 代码双向对齐（本方案核心增量）

**正向（字典→代码）**：每条字典指标找代码实现
1. 精确匹配：名称/别名 == 输出字段名（含词根拆解后的归一化比较）
2. 公式匹配：字典公式文本 ↔ SQL 聚合链（正则+归一化，"SUM(支付金额)"↔SUM(pay_amount)+注释"支付金额"）
3. 语义匹配：LLM 对剩余未匹配项打分（字典描述 + DDL 注释 + SQL 上下文 → top-k 候选）

**反向（代码→字典）**：未匹配的代码候选 = 孤儿口径

**冲突/漂移三层检测**：
| 层 | 检测 | 含义 |
|---|---|---|
| L1 字典内部 | 同名不同义 / 同义不同名 | 字典本身脏 |
| L2 代码内部 | 同名指标多实现（COUNT vs COUNT DISTINCT） | 重复建设/口径分裂 |
| L3 字典 vs 代码 | 字典公式 ≠ 代码实现 | **意图漂移**（最危险：字典说一套代码跑另一套） |

**置信度分流**（决定人审工作量）：
- **C3 自动定案**：名称精确匹配 + 公式匹配成功 → 直接入体系
- **C2 快速确认**：名称匹配但公式含糊/多实现 → LLM 给建议，人批量点确认
- **C1 人工队列**：名称对不上（字典叫 GMV 代码叫 total_pay_amt）→ LLM 语义候选 top-3 + 人审

### S3 LLM 口径富化

上下文 = 字典条目 + DDL 注释 + ETL SQL + 血缘链，产出**口径卡片**：

```json
{
  "metric_id": "M-1024",
  "名称": "PC端日支付金额", "别名": ["pay_amt_1d_pc"],
  "层级": "原子:支付金额 + 修饰:PC端 + 周期:自然日",
  "口径描述": "统计自然日内PC渠道(pay_channel='pc')已支付订单(pay_status=4)的应付金额总和",
  "计算逻辑": "SUM(pay_amount)",
  "过滤条件": ["pay_status=4", "pay_channel='pc'"],
  "维度": ["buyer_id"],
  "源链": "ods_trade_orders → dwd_trade_pay_info → dws_trade_pay_pc_1d.pay_amt_1d",
  "实现处": 1, "字典一致": true, "置信度": 0.95,
  "负责人": "（继承字典）"
}
```

对字典已有描述的条目：**做差异检测给修订建议，不擅自重写**（保留人的语义权威）。

### S4 人审回填 + 防漂移

- 人审：Excel 批审（C2 批量确认 + C1 逐条）或简单 Web 面板
- 回填 DataWorks：口径卡片 → 数据指标模块 Excel 批量导入（原子指标/修饰词/时间周期/派生指标分四个 sheet，列映射以你们实例的实际模板为准）；或落自建语义层（cubepy measure YAML）
- 防漂移：周跑增量——新脚本/字典变更 → diff 已入库口径 → 漂移告警

## 3. 精确度边界（诚实声明）

| 环节 | 精确度 | 保证方式 |
|---|---|---|
| SQL 聚合/过滤/血缘提取 | 100%（机器可证） | sqlglot AST，解析失败降级标记不猜 |
| 命名拆解 | 高 | 公司词根表 + 人工确认一次 |
| 字典↔代码对齐 | C3 全自动 / C2/C1 人审兜底 | 置信度分流，宁可疑不武断 |
| 口径文字 | 草稿质量 | 人审定稿，LLM 只起草 |
| 血缘多跳穿透 | 受 SQL 质量限制 | 动态 SQL/脚本节点标记"断链"，不给假链 |

**"最大程度精确"的实现方式不是让机器全对，而是：机器保证确定的部分全对 + 不确定的部分明确标出并给人最小审核面。**
