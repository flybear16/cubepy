# 07 — 预聚合（Pre-aggregation）方案调研

> **状态（2026-08）：已实现 MVP。** 本文原为调研结论，现其建议的同 DB 物化 rollup +
> aggregate-navigation 方案已落地（SUM/COUNT 可加度量、单 cube、UTC 时间粒度对齐、RLS 列覆盖、
> APScheduler 定时刷新、fail-closed 回退）。实现细节与用法见 [08-preaggregation-usage.md](./08-preaggregation-usage.md)。
> 下方「决策清单」中针对 Postgres/DuckDB 的 MVP 分支即为已采用路线。

> 范围：不局限于 cube.js。覆盖「把聚合提前算好、查询时命中」这一类技术的全部主流形态，
> 并给出 CubePy 的落地建议。本文是调研结论，**不是**实现 —— CubePy 当前 `PreAggRouter` 仍是空实现（seam）。

## 一、为什么需要预聚合

分析型查询的瓶颈几乎都在「扫描大表 + 分组聚合」。三种缓解手段，成本/收益递增：

| 手段 | 算什么 | 复用粒度 | 失效控制 | CubePy 现状 |
|---|---|---|---|---|
| **结果缓存** | 缓存整条查询的最终结果 | 单查询（精确匹配） | TTL / refreshKey | ✅ 已有（Redis） |
| **预聚合** | 预先按某些维度组合算好汇总表 | 多查询（同维度组合可复用） | 定时/CDC 刷新 | ❌ stub |
| **物化视图（DB 层）** | DB 引擎自己维护的预计算 | 同上，但维护在 DB 内 | DB 自管 | ❌ 未用 |

结果缓存命中条件最严（查询必须完全一致）；预聚合放宽到「维度组合一致」即可复用，是性价比最高的一档。
CubePy 现在只有结果缓存，所以**缺的就是中间这一档**。

## 二、三个正交维度

任何预聚合方案都在这三个轴上做选择：

1. **构建模型** — 全量重算 / 增量（diff）维护 / 流式（写入即算）。
2. **刷新触发** — 定时调度 / 按需（查询时 miss 触发）/ 数据变更（CDC、触发器）。
3. **匹配/改写** — 手动指定 / 声明式自动路由 / 引擎透明改写。

难点集中在第 3 个：**判断一个查询能否安全地用某张预聚合表回答**（聚合导航 / aggregate navigation）。

## 三、主流方案对比

### 1. 应用层 rollup 表 + 查询改写（cube.js 派）

应用自己建一张汇总表（`SELECT 维度, 聚合 FROM 原表 GROUP BY`），查询时由应用判断能否改写到这张表。

- 优点：不依赖 DB 能力；跨数据源统一；可做多 cube 组合匹配。
- 缺点：**匹配算法是硬骨头**（见第五节）；刷新逻辑要自己写。
- 代表：cube.js（见第四节）、Apache Superset（materialized dataset，手动）。

### 2. 数据库物化视图 — Postgres `MATERIALIZED VIEW`

DB 原生声明式：`CREATE MATERIALIZED VIEW ... AS SELECT ...`。

- 刷新：`REFRESH MATERIALIZED VIEW`，**全量重算**；`CONCURRENTLY` 需唯一索引、不阻塞读。
- 增量：核心 PG **没有**增量维护（截至 PG 18）；要靠 [pg_ivm](https://github.com/sraoss/pg_ivm) 扩展。
- 匹配：PG **不会自动改写**查询去命中物化视图 —— 你得自己把查询指向视图名。Oracle/Spark 等才有透明 MV 改写。
- 优点：声明式、DB 原生、事务一致。
- 缺点：全量刷新贵；不自动改写；增量要装扩展。

### 3. 增量/流式物化视图（数仓引擎内置）

写入或调度时只算变化部分（delta），近实时维护。

| 引擎 | 增量方式 | 触发 |
|---|---|---|
| ClickHouse | `MATERIALIZED VIEW ... TO table`，**插入时增量**触发 | 写入 |
| Hologres 动态表 | 引擎自动增量维护，秒~分钟级 | 自动 |
| Snowflake / BigQuery | MV，后台增量刷新 | 调度 |
| Redshift | late-binding MV，自动/手动刷新 | 调度 |
| Databricks | [增量刷新 MV](https://docs.databricks.com/aws/en/ldp/incremental-refresh)，检测源变化只算差异 | 调度 |
| [RisingWave](https://risingwave.com/blog/incremental-materialized-views-complete-guide/) / [Materialize](https://materialize.com) | 流式增量（真 streaming engine） | 流/CDC |

这一档最省心 —— 但**前提是底层是这些引擎**。CubePy 若跑在原生 Postgres / DuckDB 上，享受不到。

### 4. OLAP 预计算引擎（cube-on-disk）

把多维组合**全部**预先算出来（N 维交叉），存储为 cube，查询时切片。

- **Apache Kylin**：构建 cube（可选聚合组控制组合爆炸），存 Parquet/HBase，SQL 经路由命中 region；强在超大规模预计算，重在建模与构建调度。
- **Apache Druid**：摄入时按 `granularitySpec` 做 rollup 聚合，存 segment；近实时，但维度基数大时 rollup 率下降。本质是「摄入期预聚合」，不是查询期改写。

### 5. 变换层（dbt）

[dbt](https://docs.getdbt.com/) 的 incremental model + metrics 层：在 pipeline 里把汇总表定义成 model，按调度跑。
不解决「查询自动改写」，但解决了「汇总表的版本化、测试、调度」—— 常和上面的应用层路由配合。

### 6. DuckDB 的现状（重要，因为 CubePy 已支持 DuckDB）

- DuckDB **没有原生 `CREATE MATERIALIZED VIEW`**，也没有增量刷新（截至 2026）。
- 官方做法是 `CREATE TABLE roll AS SELECT ...`（CTAS），刷新即全量重跑。
- DuckDB 官方博客明确表态：流式/增量物化视图**不是**它的定位，建议把 [RisingWave / Materialize](https://duckdb.org/2025/10/13/duckdb-streaming-patterns) 放在 DuckDB 上游做增量，DuckDB 只管查询。社区有 [MV 讨论](https://github.com/duckdb/duckdb/discussions/3638) 但未落地。
- 关键判断：**DuckDB 列式 + 向量化执行足够快，中小数据量常常根本不需要预聚合**；上量后再上 CTAS rollup（全量）或前置流式引擎。

## 四、cube.js 的具体设计（从源码/官方文档摘取）

cube.js 是「应用层 rollup + 自动改写」路线最完整的实现，值得作为蓝本：

- **rollup 存在哪**：Cube Store（自研 Rust/Arrow OLAP）—— 不是源库。预聚合是独立存储层。
- **类型**：`rollup`（指定维度组合）/ `original_sql`（缓存原 SQL 子查询）/ `autoRollup`（引擎自动选组合）。
- **刷新**：`scheduledRefresh` + `refreshKey`（`every`/`sql`/`updateWindow`）+ `partitionGranularity`（按时间分区增量刷新，避免整表重算）+ 多时区矩阵（`scheduled_refresh_time_zones`）。
- **匹配算法**（[官方](https://cube.dev/docs/pre-aggregations/matching-pre-aggregations)）核心校验：
  1. 查询里所有 leaf measure 必须是**可加的**（sum/count/可加的 distinct 等；非可加 measure 如 median、复杂 distinct 不能用 rollup）。
  2. 预聚合必须**覆盖**查询用到的所有维度、过滤维度、leaf measure。
  3. 时间维度按**粒度 GCD 对齐**（day 与 hour 的公共粒度是 hour）。
  4. **时区必须匹配**（按预聚合构建时声明的时区集合）。
  5. 过滤维度若同时是查询维度才能匹配；`switch` 维度可豁免。
  6. 多事实 / 多阶段查询会拆成多个子查询，每个独立匹配，全部命中才整体走预聚合。
- **改写**：命中后，把对原表的查询改写成对 rollup 表的查询（粒度更细时再二次聚合）。新版由 **Tesseract** planner 执行。

要点：cube.js 把「匹配 + 改写」做成了产品里最复杂的部分。**这是自建预聚合最大的工程量来源。**

## 五、查询改写 / 聚合导航难题

为什么这件事难：判断「这张汇总表能不能回答这个查询」是个约束满足问题：

- **维度可加性**：rollup 必须按查询维度（或其超集）分组，才能再聚合回查询粒度。
- **度量可加性**：sum/count 可加（对 rollup 再 sum 正确）；count distinct 不可加（需存 HLL/Theta sketch）；avg/min/max 部分可加。
- **时间粒度对齐**：rollup 按 day 分组，能回答 hour 查询吗？不能（信息已丢失）；能回答 month 吗？能（再聚合）。
- **过滤下推**：查询的 WHERE 必须能用 rollup 的列表达，否则不能命中。

历史上有 MicroStrategy 的「aggregate awareness」、Oracle OLAP、SSAS 的聚合设计；现代趋势是两极：要么**引擎内置透明改写**（Spark/Oracle/Doris），要么**应用层显式路由**（cube.js）。CubePy 走应用层，意味着要自己实现这套校验。

## 六、对 CubePy 的建议

**前提纠正**：项目文档（01/02/05）是调研，实际**没有用 Hologres**。所以「Hologres 动态表替你做预聚合」这个跳过理由**不成立**。CubePy 的真实底层是原生 Postgres（或 DuckDB）。结论：**预聚合值得做**，但要分层、按底层选型。

### 按底层选型

| 底层 | 推荐主路径 | 理由 |
|---|---|---|
| **Postgres** | 应用层 rollup 表 + cube.js 风格匹配器（接现有 `PreAggRouter` seam），刷新走 APScheduler；增量可选用 `pg_ivm` 维护底层 MV | 核心无增量 MV；pg_ivm 还是扩展、不够稳；应用层路由最可控 |
| **DuckDB（中小数据）** | **先不做预聚合** —— DuckDB 向量化引擎常常够快 | 增量 MV 不存在；CTAS 全量刷新；上量再说 |
| **DuckDB（大数据）** | CTAS rollup 表定时全量刷新；或上游接 RisingWave/Materialize 做流式增量 | DuckDB 自己不做流式 |
| **ClickHouse / Hologres / Snowflake / BQ** | 直接用引擎的增量 MV，**应用层不做** | DB 已经替你做了，应用层重复造轮子没意义 |

### 推荐 MVP 实现路径（Postgres / DuckDB 通用）

接现有的 `PreAggRouter` seam，做最小可用版本：

1. **定义**：cube 上声明 `pre_aggregations: [{name, measures, dimensions, time_dimension, granularity, refresh_key}]`（对齐 cube.js YAML，降低学习成本）。
2. **存储**：rollup 表名 `cubepy_rollup_<cube>_<name>`，`CREATE TABLE ... AS SELECT ... GROUP BY ...`。
3. **构建/刷新**：APScheduler（已是依赖）按 `refresh_key.every` 调度；增量先用**分区全量**（按 `partitionGranularity` 分时间片，只刷近期分区），不做 delta。DuckDB 上就是 CTAS 重跑。
4. **匹配器**（最小版，先砍掉难点）：
   - 覆盖检查：rollup 的 measures ⊇ 查询 leaf measures、dimensions ⊇ 查询 dimensions。
   - 可加性：查询 measure 必须可加（sum/count/countDistinctApprox if sketch stored）。
   - 时间粒度：rollup 粒度须 ≤ 查询粒度（能再聚合上去）。
   - **先不做**：多时区矩阵、多事实拆分、autoRollup、switch 维度豁免、非可加 measure 的 sketch 支持。
5. **改写**：命中后，把 SQL 的 FROM 指向 rollup 表，SELECT 对 rollup 列再聚合（粒度上卷）。
6. **可观测**：`/load` 响应里已有的 `usedPreAggregations` 字段填上命中信息（现在恒空）。

### 何时**不**做（避免过度工程）

- 底层是 ClickHouse / Hologres / Snowflake / BigQuery / Redshift —— 用 DB 的 MV。
- DuckDB + 查询响应已达标（P95 < 目标）—— 别提前优化。
- 查询模式高度发散、维度组合爆炸 —— rollup 命中率低，不如扩结果缓存。

### 决策清单

- [ ] 确认真实底层 DB（Postgres？DuckDB？ClickHouse？）
- [ ] 若 Postgres/DuckDB：是否查询慢到需要预聚合（有 P95 数据吗）？
- [ ] 若要做：MVP 是否只做可加 measure + 单 cube + 时间粒度对齐？（建议是）
- [ ] 增量需求强吗？强 → Postgres 上 pg_ivm 或换 ClickHouse；不强 → 分区全量刷新即可。
